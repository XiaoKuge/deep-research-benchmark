# 模拟评审使用说明（tools/simulate_review.py）

还没有真人评委的阶段，主办方用这个程序让几家模型按[评审细则](../research-plan/stage4-rubric.md)第 1.2 版评审一道题的一组报告：列主要结论清单、断言核验、要点抽取、合并要点池、逐条判定要点、环节评级、两两比较、标出对题目的直接回答。各步用哪几家、每家几次可以配置；多位评委的意见按下文"判定怎样合并"的规则合成一份，写成[计分程序](../research-plan/stage5-pilot/score.py)第 1.2 版能读的数据目录，再直接调用计分程序，产出结果文件。依据还有[规则手册](../research-plan/rules.md)第七节（评审五步、评委组）和第八节（名次、有争议的标注）。

模型一律通过[模型调用层](models.md)（`tools/models.py`）调用，每一次调用的提示词全文、回答全文、厂商、模型和时间都记进调用记录。评委提示词的模板在 [review_prompts/](review_prompts/)，以第五阶段存档的[评委提示词](../research-plan/stage5-pilot/judges/README.md)为起点改写。只用 Python 自带的标准库。测试在 `tests/test_simulate_review.py`，一律用回放方式，不真的调用模型。

文中的 JSON 是一种纯文本的数据格式；评委每一步都只回答一个 JSON 对象，程序再按规则合并、写文件。

## 一条命令

先只估算，看要调用几次（不调用任何模型）。下面用第五阶段的题目和试评的六份报告：

```
python3 -I tools/simulate_review.py \
    --question simulation/questions/第五阶段试评题 \
    --reports research-plan/stage5-pilot/reports/*.md \
    --keep-labels --names research-plan/stage5-pilot/mapping.json \
    --estimate
```

用默认配置，这一条打印 181 次：结论清单 6，断言核验 42，要点抽取 18，要点池合并 1，写到核对 6，要点判定 6，环节评级 36，两两比较 60，直接回答 6。

再在调用次数上限内真跑（真实调用必须给 `--max-calls`）：

```
python3 -I tools/simulate_review.py \
    --question simulation/questions/第五阶段试评题 \
    --reports research-plan/stage5-pilot/reports/*.md \
    --keep-labels --names research-plan/stage5-pilot/mapping.json \
    --config 配置.json --run-id 试评重评-1 --max-calls 200
```

照一份录好的调用记录重放，不调用模型（测试就是这样跑的）：

```
python3 -I tools/simulate_review.py --question …… --reports …… \
    --replay simulation/reviews/试评重评-1/calls.jsonl --run-id 试评重评-1-重放
```

| 选项 | 作用 |
| --- | --- |
| `--question 题目目录` | 必填。题目目录，格式见"输入"一节。 |
| `--reports 报告文件……` | 必填，至少两份。Markdown 或网页（`.html`、`.htm`）文件。 |
| `--keep-labels` | 报告已经匿名（例如试评的 A 至 F）时加上：用文件名（不带扩展名）作报告编号。不加时，程序按随机种子把报告打乱，编为 A、B、C…… |
| `--names 名称表` | 可选。JSON 文件，`{文件名（不带扩展名）: 产品或队伍名}`；也接受试评 `mapping.json` 的写法（名称放在 `reports` 下）。名称只写进输出目录的 `mapping.json`，评委看不到。不给就用文件名。 |
| `--archive 存档目录` | 可选。[网页存档程序](archive_sources.md)写出的存档目录，或者放着几个这种目录的上一级目录：程序找出其中所有的 `manifest.json`。 |
| `--config 配置文件` | 可选。各步用哪几家、每家几次等，见"配置"一节。 |
| `--estimate` | 只估算：不调用模型，把整个流程用占位回答走一遍，打印将发起的调用次数。 |
| `--replay 调用记录……` | 回放：回答从录好的调用记录里取，可以给几个文件。 |
| `--max-calls N` | 真实调用的次数上限。真实调用时必须给；只估算时用来判断会不会超过。 |
| `--run-id 运行标识` | 运行标识，默认用开始时间，例如 `20261030-153000`。 |
| `--out 输出目录` | 默认 `simulation/reviews/<运行标识>/`。目录已经有内容时拒绝运行，不覆盖。 |
| `--cutoff 日期` | 截止日期，例如 `2026-03-03`。不给就从题目卡"截止时间"一行读出日期；模拟出题者写的是"〔运行当日〕"，没有日期，这时要用这个选项给出智能体的运行日期，否则提示词里只能写"以题目卡为准"。 |
| `--workers N` | 同时进行的调用数，默认 4。 |
| `--seed N` | 随机种子，默认 0：用于报告编号、两两比较哪种先后算"第一种"、要点判定时要点的排列顺序。 |

退出状态：

- 0：评审完成，结果文件写好了。打印每份报告的名次区间。
- 1：评审中途停止，例如各家都不可用、只有一位评委的步骤回答无效、到了调用次数上限、回放时缺了某一步的回答。输出目录里有 `run.json`（`status` 为"中止"，`error` 写明原因）和已经发生的调用记录，没有结果文件。
- 2：选项、配置或输入有问题，或者输出目录已经有内容，或者真实调用时估算的次数超过上限。这时一次也不调用。

## 输入

**题目目录。** 格式照[模拟出题者](simulate_setter.md)的"输出目录"一节。评审要用的是：

- `题目卡.txt`：必需。整个文件交给评委，评委版的提问者、用途、问题、截止时间都在里面。
- `深度地图.json`：必需。程序读其中的"要点"：编号、要点、层级、重要性。编号 1 在评审里记作 M1，以此类推。
- `深度地图.txt` 和 `深度地图校验值.txt`：可选。有就算出 `深度地图.txt` 的校验值，核对和校验值文件是否一致，结果记进 `run.json`。
- `元数据.json`：可选。有就记下"类别"（练习题或正式题）。

深度地图的全文不交给任何评委；评委只在合并和判定两步看到地图的要点（带登记的层级和重要性）。

第五阶段的题目已经转成这个格式：[simulation/questions/第五阶段试评题/](../simulation/questions/第五阶段试评题/元数据.json)。原题没有提问版，也没有附交付要求，所以目录里没有交给智能体的两个文件；地图是读过部分报告之后才写的，只有一位出题人。这些在目录里的 `元数据.json` 和两个文本文件里都写明了。

**报告和匿名化。** 评委看不到报告的原名：

- 不加 `--keep-labels` 时，程序按随机种子打乱报告，编为 A、B、C……；原名和原文件路径只写进输出目录的 `mapping.json`。
- 报告副本按编号存进输出目录的 `reports/`。正文一字不改（规则手册第七节要求去掉队伍名和产品名；正文里出现的名字，要在交给程序之前处理好，见"已知的局限"）。
- 只涉及一份报告的步骤，提示词里连报告编号也不出现，只说"这份报告"；结论用 c1、c2 这样的局部编号。

**网页存档。** 一条存档算"可用"，要同时满足：清单里有内容文件，没有错误原因，状态码小于 400，内容是网页或纯文字。网页去掉标签、脚本和样式，只留文字。PDF 等读不出文字的内容，按没有存档处理。网址按去掉 `#` 之后的部分、百分号编码还原、去掉末尾斜杠来对应。

## 评审各步怎样变成调用

| 细则的步骤 | 调用的任务名 | 默认评委 | 工具限定 | 评委看到的材料 | 产出 |
| --- | --- | --- | --- | --- | --- |
| 第五节 结论清单 | 评审-结论清单：报告 A，评委 1 | claude 一次 | 只给材料 | 细则、题目卡、这份报告 | 这份报告的主要结论清单，所有核验员共用 |
| 第五节 断言核验 | 评审-断言核验：报告 A，只给材料，评委 n | claude、codex、kimi 各两次 | 只给材料；所引网址没有可用存档的那一组只读网页 | 细则、题目卡、这一组结论（原文、所引来源），以及所引网页的存档文字 | 每条结论的来源标签和对错标签 |
| 第三节 要点抽取 | 评审-要点抽取：报告 A，评委 n | 三家各一次 | 只给材料 | 细则、题目卡、这份报告 | 至多 20 条要点 |
| 第四节 合并 | 评审-要点池合并：评委 1 | claude 一次 | 只给材料 | 细则、题目卡、地图要点（带登记值）、全部抽取的要点、全部主要结论（带核验结果） | 池中要点和它由哪些条目合并而来 |
| 第四节 记下写到了哪些 | 评审-写到核对：报告 A，评委 n | claude 一次 | 只给材料 | 题目卡、这份报告还没记到的池中要点（只有编号和内容）、这份报告 | 这份报告还写到了哪些要点，符合还是相反 |
| 第四节 判定 | 评审-要点判定：评委 n | 三家各两次 | 只给材料 | 细则、题目卡、要点池：只有编号和内容，地图上的要点另附登记的层级和重要性；顺序每位评委各自打乱 | 对不对、切不切题、层级、重要性 |
| 第二节 环节评级 | 评审-环节评级：报告 A，评委 n | 三家各两次 | 只给材料 | 细则、题目卡、这份报告 | 五个环节和写作的档位（每项引原文）、时效、答非所问、有没有可追溯的来源 |
| 两两比较 | 评审-两两比较：A 在前，B 在后，评委 n | claude、codex 各一次，每对两种先后各比一次 | 只给材料 | 细则、题目卡、两份报告，称"第一份""第二份" | first、second 或 tie |
| 第五节 直接回答 | 评审-直接回答：报告 A，评委 n | claude 一次 | 只给材料 | 题目卡、这份报告的主要结论清单 | 至多 3 条对题目的直接回答 |

几点说明：

- **评委编号。** 每一步里按配置的顺序编号：先排第一家的各次，再排第二家的，例如默认的断言核验，评委 1、2 是 claude，3、4 是 codex，5、6 是 kimi。厂商被替代时编号不变。
- **两档工具限定。** 评审各步一律只给材料：不能上网、不能运行命令、不能读写文件。只有断言核验里"引了网址、却没有可用存档"的结论单独分一组，这一组只读网页，让核验员打开所引网址。没有网址的结论，来源标签直接定为"没有出处"，核验员只判定对错；清单员写的网址在报告里找不到的，不算网址。
- **写到核对。** 合并一步只能从条目的来源推出"哪份报告写到了"；细则第四节还要求"记下每份报告写到了哪些池中要点"，所以另加这一步，逐份报告核对它还写到了哪些（例如地图上的要点没被抽出来）。它只补记合并时没有的，不改合并的结论。
- **要点判定隐去出处。** 提示词里没有报告编号、条目编号，也不说一条要点出自几份报告；合并一步要求要点内容里不提报告。测试会检查要点判定的提示词里不出现任何报告编号和条目编号。
- **编号的写法。** 地图要点 M1、M2……；主要结论"报告编号-c序号"，例如 A-c3；抽取的要点"厂商-评委编号:报告编号-序号"，例如 claude-1:A-3；池中要点 Q1、Q2……

## 判定怎样合并

标签取多数，档位取中位数；层级和重要性用三分之二规则。具体是：

| 判定 | 规则 | 票数相同时 |
| --- | --- | --- |
| 来源标签 | 多数 | 取对报告影响最轻的：支持、部分支持、失效但有存档、没有出处、不支持、找不到（疑似编造），按这个顺序取靠前的 |
| 对错标签（结论、要点） | 多数 | 记为无法判断 |
| 切不切题 | 多数 | 算切题 |
| 写到核对 | 多数（符合、相反、没写到） | 算没写到 |
| 层级、重要性 | 三分之二规则，见下 | 见下 |
| 五个环节和写作的档位 | 每次评级写一个文件，计分程序取中位数 | |
| 答非所问 | 计分程序取多数 | |
| 时效 | 环节评级各次的中位数 | |
| 有没有可追溯的来源 | 环节评级各次取多数；有结论的来源标签是支持、部分支持、不支持或失效但有存档的，直接算有 | 算有 |
| 对题目的直接回答 | 过半数评委挑到的结论；没有一条过半时，取票数最多的，至多 3 条 | |
| 两两比较 | 每次的判定原样交给计分程序，由它按规则手册第八节第 4 条否决 | |

"找不到（疑似编造）"必须写了第二次核查（`second_check`）才算一票，这是细则第五节的要求。

**三分之二规则**（细则第四节末尾，规则手册第八节第 5 条）：

- 有一种意见的票数达到总票数的三分之二（票数 × 3 ≥ 总票数 × 2），就用它，没有争议。
- 但它若改动了地图登记的标注，算"评委组改动过的地图标注"，记为有争议，写成候选列表：地图登记在前，评委组的意见在后。
- 没有一种意见达到三分之二，记为有争议，写成候选列表。第一项是登记值：地图上有的用地图登记；没有的用票数最多的，并列时取较浅的层级或"一般"。其余候选按票数从多到少、再由浅到深排列。
- 地图上的要点，评委改动登记值却没写理由（`change_reason`）的，这一票按登记值计。
- 漏判的评委不算票：一条要点只有两位评委判了，两票各一，就有争议。

计分程序第 1.2 版读到候选列表，比较一对报告时按对领先一方最不利的那种标注计分，所以有争议的判定只能让一对报告并列，不能把它们拉开。

测试里的几个例子（三位评委）：

| 三位评委的意见 | 地图登记 | 写进要点池 |
| --- | --- | --- |
| 本质、本质、全体 | 没有 | 本质 |
| 本质、全体、内部联系 | 没有 | ["全体", "内部联系", "本质"] |
| 核心、一般，第三位漏判 | 没有 | ["一般", "核心"] |
| 全体（写了理由）、全体（写了理由）、本质 | 本质 | ["本质", "全体"] |
| 全体、全体、本质（没写理由） | 全体 | 全体 |

**人工审计。** 地图上没有、候选里有"核心"的要点，列进 `run.json` 的 `audit_points`（规则手册第七节：判为核心的列入人工审计）。环节评级的引文在报告里找不到的，列进 `notes.evidence_not_found`，档位不自动改动，留给人工核对。

## 配置

配置是一个 JSON 文件，只写要改的项，其余用默认值：

```
{
  "steps": {
    "verify": {"vendors": ["claude", "codex"], "times": 2},
    "judge": {"vendors": ["claude", "codex", "google"], "times": 2}
  },
  "models": {"claude": "claude-opus-5-5"},
  "substitutes": ["claude", "codex", "kimi", "google"],
  "source_chars": 12000,
  "workers": 4,
  "seed": 0
}
```

| 项 | 含义 | 默认 |
| --- | --- | --- |
| `steps` | 每一步用哪几家（`vendors`）、每家几次（`times`）。步骤名：`claims_list` 结论清单、`verify` 断言核验、`extract` 要点抽取、`merge` 要点池合并、`reach` 写到核对、`judge` 要点判定、`rating` 环节评级、`pairwise` 两两比较、`direct` 直接回答 | 见上一节的"默认评委" |
| `models` | 每一家用哪个模型；不写或写 `null` 用该命令行的默认模型 | 都用默认模型 |
| `substitutes` | 某一家不可用时，按这个顺序找替代 | claude、codex、kimi、google |
| `source_chars` | 每个网址的存档文字至多附多少字 | 12000 |
| `workers` | 同时进行的调用数（命令行的 `--workers` 优先） | 4 |
| `seed` | 随机种子（命令行的 `--seed` 优先） | 0 |

厂商名是模型调用层认得的四家：`claude`、`codex`、`kimi`、`google`（Google 的 Antigravity 命令行 `agy`）。结论清单和要点池合并按细则只由一位评委做，只能配一家、一次，否则拒绝运行。写了不认识的项或步骤，也拒绝运行。

默认配置按规则手册第七节"至少三家厂商的模型担任评委，每个评委评两次"：断言核验、要点判定、环节评级都是三家各两次；两两比较按第八节第 4 条"两位评委各按两种先后比一次"。

## 厂商不可用时

一次调用失败、超时或找不到命令行（模型调用层抛出调用失败），程序就把这一家记为本次运行中不可用，后面不再用它，这一次和以后轮到它的调用都换一家：按 `substitutes` 的顺序，先挑这一步没配的厂商（尽量让评委仍来自不同厂商），没有再挑这一步已经配了的。换来的这家也不可用，再往下换；一家可用的都没有，评审停止（退出状态 1）。

- 每一家不可用的原因（第一次失败的任务和模型调用层记下的错误）写进 `run.json` 的 `unavailable`；每一次替代（哪一步、哪个任务、配置的是哪家、实际用了哪家）写进 `substitutions`；各步实际用了哪几家、每家几次、什么模型，写进 `steps`。真实调用时，失败的那次调用本身也在调用记录里。
- 不可用的那一家不会有任何判定：它的评委位置要么由替代的厂商完成，要么评审停止。程序不伪造结果。
- 每一次失败都算进调用次数上限。为了不白费调用，每一家在第一次调用成功之前，同一时间只发一个调用：同时进行几个调用时，一家不可用也只多一次失败的调用。

**现在的情况。** 本机 kimi 的登录已经过期；Google 的 `agy` 已经登录（2026 年 10 月 30 日），评审各步都是只给材料档，google 可以当评委（见 [models.md](models.md)）。下面描述的是 google 不可用时的情形。用默认配置真跑时，kimi 的第一次调用会失败，它的位置先换成 google（默认的各步都没配 google），google 也失败，再换成 claude，一共多两次失败的调用；这时断言核验、要点判定和环节评级的评委只来自两家，`run.json` 里写明。想省掉这两次失败，可以在配置里直接不用 kimi，但那样 `run.json` 里就不会记下 kimi 不可用。

## 只估算和调用次数上限

- `--estimate` 不调用模型，把整个流程用占位回答走一遍，`calls.jsonl` 里每次调用一条状态为"未调用"的记录，`run.json` 写出按厂商、按步骤的次数；不写数据目录和结果文件。
- 估算是上限。还没有结论清单，断言核验按报告里的网址分组：每份报告一组只给材料，报告里有没存档的网址再加一组只读网页；真跑时某组没有结论就少一次。写到核对每份报告各算一次；真跑时一份报告已经写到了池中全部要点，就不调用。
- 估算假定配置的厂商都可用。某一家不可用时，每换一家多一次失败的调用。
- 真实调用时，程序先自己估算一次；估算的次数超过 `--max-calls`，就不开始（退出状态 2），免得跑到一半停下。估算的次数也写进 `run.json` 的 `estimate`。
- 真跑时到了上限，评审停止（退出状态 1），已经发生的调用都在调用记录里。

## 回放材料

`--replay` 读录好的调用记录，按任务名、厂商和提示词校验值取回答（规则见 [models.md](models.md) 的"回放"一节）。录好的记录可以是上一次真实运行的 `calls.jsonl`，也可以手写；手写时每行只写 `task`、`vendor`、`answer` 三个字段，不写 `prompt_sha256`，就匹配这个任务、这一家的任何提示词。任务名照"评审各步怎样变成调用"一节的写法，每个任务名在一次运行里只出现一次，所以同时进行几个调用也不会取错。`answer` 是那一步评委该回的 JSON 文字，格式见各个[提示词模板](review_prompts/)的末尾。

回放材料里状态为"失败"或"超时"的记录，表示那一家在录制时不可用：回放时轮到这一家、又取不到它的回答，就照"厂商不可用时"一节记为不可用并换一家，原因取那条记录的 `error`。这样重放一次真实运行时，当时的替代会照样发生。测试用它模拟 kimi 登录过期、`agy` 没有登录：

```
{"task": "评审-要点判定：评委 3", "vendor": "kimi", "status": "失败", "error": "退出状态 1；……401……"}
{"task": "评审-要点判定：评委 3", "vendor": "google", "status": "失败", "error": "退出状态 1；……还没有登录"}
{"task": "评审-要点判定：评委 3", "vendor": "claude", "answer": "{\"points\": [……]}"}
```

回放时缺了某一步的回答（又没有录下那一家失败），评审停止（退出状态 1）。

## 评委提示词改写了哪些地方

模板在 [review_prompts/](review_prompts/)，`{{名字}}` 由程序换成材料：评审细则全文、题目卡全文、报告全文、结论、要点等，每段材料前后用"===== 名称（开始） ====="和"===== 名称（结束） ====="标出。细则和题目卡是运行时从文件读出来的，细则改了，提示词跟着变。

所有模板共同的改写，起点都是第五阶段存档的提示词（[judges/prompts/](../research-plan/stage5-pilot/judges/prompts/)）：

1. 原来让评委到本机目录读细则、题目卡和报告（"工作目录……先读两份文件"），现在评委不能读写文件，改为把这些材料的全文直接放进提示词，并删去"除了这些文件，不要读其他文件""不要读 out/ 下的文件"等只对能读文件的评委才有意义的规则。
2. 原来让评委把结果写进 `out/` 下的文件、用 python3 检查能否读入、最后回复一句话，现在改为"只回答一个 JSON 对象，不要写任何别的文字，也不要用代码块"，文件由程序写。
3. 原来写"不要上网"或"可以用某某工具上网"，现在按两档工具限定写明能做什么、不能做什么。
4. 原来是"小规模检验"，现在是"模拟评审"；原来把截止时间写死为 2026-03-03、并提醒"现在已是 2026 年 10 月"，现在截止时间按题目卡或 `--cutoff` 填入，改为"要注意排除截止时间之后才出现的信息"。
5. 原来一位评委一次评六份报告（还规定按正序或倒序读），现在每次调用只给一份报告（两两比较给两份），报告编号不出现在只涉及一份报告的提示词里。
6. 保留了原来的判定规则和输出字段的写法：不要猜测报告出自哪个产品、不看篇幅格式和引用条数、各项标签只能取的几个值、引原文逐字摘录。

各个模板另外的改写：

- [claims-list.txt](review_prompts/claims-list.txt)（结论清单），起点是 [verify-opus-ABCF.txt](../research-plan/stage5-pilot/judges/prompts/verify-opus-ABCF.txt) 第 1 步和 [verify-opus-DE.txt](../research-plan/stage5-pilot/judges/prompts/verify-opus-DE.txt) 里"文末来源"的写法。原来每位核验员自己抽"至多 10 条主要结论"（细则第一版）；现在按细则第 1.1 版由一位清单员列出、所有核验员共用：带来源的结论全部列入，另加至多 10 条不带来源的。新增 `urls` 一栏，要求逐字照抄报告里以 http:// 或 https:// 开头的网址，并写明引注标记、不带协议的域名和来源图标的图片地址都不算。
- [verify.txt](review_prompts/verify.txt)（断言核验），起点是 [verify-opus-ABCF.txt](../research-plan/stage5-pilot/judges/prompts/verify-opus-ABCF.txt) 第 2、3 步和 [verify-sonnet-subset.txt](../research-plan/stage5-pilot/judges/prompts/verify-sonnet-subset.txt)（拿到一张现成的结论表再核验）。原来让核验员用网页工具打开网址、链接打不开时查第三方存档；现在有主办方存档的，把存档文字放进提示词，只给材料，提醒"只附了前面一部分的，在没附的部分里找不到，不能据此判为不支持"；没有可用存档的那组才只读网页，保留查第三方存档的说法。新增：没有网址的结论来源标签已定，只判对错；"找不到"必须写第二次核查，否则不算数；没有把握的标"无法判断"。原来的时效和可追溯来源两项移到了环节评级，因为一次核验调用只看到一组结论，看不到整份报告。
- [extract.txt](review_prompts/extract.txt)（要点抽取），起点是 [rating-opus-1.txt](../research-plan/stage5-pilot/judges/prompts/rating-opus-1.txt) 第 3 步。原来和环节评级在同一次运行里做，现在单独一步；编号由程序加，评委只写内容、层级和原文；把细则第三节"同一个意思只算一条""只罗列名字的不算""套话不能定为本质"写进规则。
- [merge.txt](review_prompts/merge.txt)（要点池合并），起点是 [pool.txt](../research-plan/stage5-pilot/judges/prompts/pool.txt) 第 1 步。原来合并和判定由同一位评委一次做完；现在合并只看意思是否相同，对错、切题、层级、重要性交给后面的多位评委。原来由合并者打开报告记下"写到了哪些报告"；现在合并者只写每条池中要点由哪些条目合并而来（`sources`）、其中哪些写的是相反的版本（`opposite`），"写到了哪些报告"由程序从来源推出。新增：要点内容里不许提到报告，深度地图的每条要点都必须收进来。
- [reach.txt](review_prompts/reach.txt)（写到核对），起点是 [pool.txt](../research-plan/stage5-pilot/judges/prompts/pool.txt) 第 3 步"怀疑某份报告也写到了、只是没被抽取出来，请打开原文核对"。改成每份报告单独一次：只给这份报告和它还没记到的要点（只有编号和内容），要求只列写到了的，并引一句原文。
- [judge.txt](review_prompts/judge.txt)（要点判定），起点是 [pool.txt](../research-plan/stage5-pilot/judges/prompts/pool.txt) 第 2 步。新增细则第 1.2 版的两条：判定时不告诉评委要点出自哪份报告、出自几份报告；地图上的要点以登记值为默认值，改动必须在 `change_reason` 里写明理由，不写理由的改动按默认值计。原来的"已经有核验结果的主要结论，可以沿用核验的判断"删去，因为评委看不到要点出自哪条结论。
- [rating.txt](review_prompts/rating.txt)（环节评级），起点是 [rating-opus-1.txt](../research-plan/stage5-pilot/judges/prompts/rating-opus-1.txt) 第 1、2、4 步，以及 [verify-opus-ABCF.txt](../research-plan/stage5-pilot/judges/prompts/verify-opus-ABCF.txt) 第 4、5 步（时效、可追溯来源）。把细则"原文中找不到依据时，按较低的一档评"写进第 1 步，并说明程序会核对引文是否出自报告。
- [pairwise.txt](review_prompts/pairwise.txt)（两两比较），起点是 [pairwise-opus-fwd.txt](../research-plan/stage5-pilot/judges/prompts/pairwise-opus-fwd.txt) 和 [pairwise-opus-rev.txt](../research-plan/stage5-pilot/judges/prompts/pairwise-opus-rev.txt)。原来一次读完六份报告、按给定顺序比 15 对；现在每次只比一对，两份报告称"第一份""第二份"，同一对的另一种先后是另一次调用；删去"不要先排出总名次"（每次只有一对，排不出总名次），新增"先后顺序不代表任何倾向"。
- [direct.txt](review_prompts/direct.txt)（直接回答），起点是 [direct-answers.txt](../research-plan/stage5-pilot/judges/prompts/direct-answers.txt)。原来一次标十份报告、读 `claims-list.md`、可以打开报告原文确认；现在每次只给一份报告的结论清单（局部编号 c1、c2……），题目从题目卡里读，不再写死。

## 已知的局限

- **匿名不彻底。** 程序只换掉文件名，正文一字不改。第五阶段的话题就是各家产品，正文必然提到产品名，评委可能猜出报告出自哪里；正式比赛时，正文里的队伍名和产品名要在交给程序之前去掉。
- **只给材料的评委不能上网。** 没有网址的结论、以及要点池里要点的对错，只能依据存档和模型自己确知的知识判断，没把握的标"无法判断"。模型知识的截止日期可能早于题目的截止时间。这比试评时评委能上网核对要弱，是规格"评审各步只给材料"的代价。
- **存档的限制。** PDF 存档读不出文字，按没有存档处理（这组改为只读网页）；每个网址的存档文字只附前 12000 字（可以配置）。
- **一次失败就不再用这家。** 包括因为提示词太长、超时而失败的情况；原因都记在 `run.json` 里，需要时去掉这家或调大时长上限后重跑。
- **很长的报告。** 用试评报告时，最长的提示词约十三万字（报告 A 和 D 的两两比较）。各家命令行能接受多长的输入，没有逐一核实；超长失败会按上一条处理。
- **合并漏收的条目只记下。** 合并的评委没收进任何池中要点的抽取要点或结论，列进 `notes.not_merged`，不自动补进要点池（深度地图的要点除外，漏了由程序补上），因为补进去可能和已有的要点重复计分。
- **引文核对只标出。** 环节评级的引文在报告里找不到时（核对时统一全角半角和引号、去掉空白和 Markdown 记号），只列进 `notes.evidence_not_found`，档位不自动降低。
- **回放时按厂商重现失败。** 回放材料里只要有某一家的失败记录，回放时取不到这家的回答就当它不可用，不要求是同一个任务。
- **有争议的规则还没有检验。** 规则手册第八节写明，有争议的标注这条〔默认〕规则还没有经过检验；这个程序让它真的起作用，但它的效果要等真实运行之后再看。

## 测试

在仓库根目录运行 `python3 -I -m unittest discover -s tests -v`。本程序的测试在 `tests/test_simulate_review.py`，全部用手写的回放材料或只估算方式，不调用模型，覆盖：

- 一条命令从报告到结果文件，名次区间与手算一致；三种权重下的净分与按细则手算的一致；
- 数据目录能被计分程序第 1.2 版单独读取、算出同样的名次区间；
- 三分之二规则：恰好三分之二不算争议；三种意见各一、两票各一写成候选列表；评委组改动地图标注写成"地图登记在前"的候选列表；不写理由的改动按登记值计；有争议的要点列进运行元数据和结果文件；
- 要点判定的提示词里不含报告编号和条目编号；
- 只给材料一档：除了"引了网址却没有存档"的那组核验，所有调用都是只给材料；有存档的网址，存档文字交给了核验员；
- 厂商不可用：原因如实记下，替代逐条列出，不可用的厂商名下没有任何调用，评审照样完成；
- 只估算的调用次数（按手算）；真实调用不给上限、或上限低于估算时不开始；
- 不加 `--keep-labels` 时报告的原名不进任何提示词；
- 第五阶段的题目目录和六份报告能直接交给程序；
- 本说明的必备章节、提示词模板的改写说明和本地链接。
