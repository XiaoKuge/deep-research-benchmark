# 智能体深度研究 Benchmark（研究方案 v2）

2026-10-29 修订。v1 见同目录 `v1.md`，改动及原因见文末「修订记录」。

【问题】让多个智能体（当前为 5 个）用同一个 Prompt 做 Deep Research（DR），把它们的交付结果输入 Benchmark 系统，得出**可信的排序**：谁更强，以及这个名次有多稳。打分是排序的手段，能给出分数更好。要定义的是这套 Benchmark 的实施方案。

【工作方法】

## 0. 明确用途（先于一切定义）

1. **这个排序拿来做什么决定？** 选型、比赛排名，还是追踪进展。用途决定后面每个定义的取舍。
2. **被评对象：端到端的系统**（模型 + 工具 + 检索环境 + 运行时间），不是底层模型。记录每个 Agent 的版本、运行日期、是否联网。
3. **输出：**
   - 名次，以及名次的可信度。例："A 排第一的概率 92%，B 与 C 分不开"。
   - 各维度的分数。
   - 可选：一条绝对的及格线。如果用途里有"有没有一个够用的"，就需要它，因为只排序说不出"5 个都不合格"。
4. **质量和成本分开：** 耗时、费用单独报告，不混进质量分。

## 1. 工作定义：以共性为基线，明确写出偏离

基线取 23 篇文献的共性（推导见 `notes/overview-common-definitions.html`）：

1. **Research**：为回答用户的一个信息需求，从已有的外部信息中查找、阅读并整合证据，得出结论的过程。不产生新数据。
   - 偏离：加上"截至某个日期"。
2. **Deep Research**：由智能体自主完成的 Research。问题无法靠一次检索或单一来源回答，需要多步、多跳的搜索，并在多条信息之间推理、整合。
   - 偏离：加入场门槛。借 LiveDRBench 的门槛：专家借助搜索要 10 分钟以上、20 段以上材料。这两个数字是约定，不是证明出来的。
3. **Benchmark**：一套可重复执行的比较程序。给多个系统同一组任务，在规定的运行条件下，按事先确定的判分依据给出可比较的分数或名次。
4. **DR Benchmark**：用来比较 DR 系统的 Benchmark。任务满足第 2 条，评测对象是端到端系统，判分主要看交付结果。
   - 偏离：任务必须通过闭卷检查（不联网答不出来）；答错要比不答更吃亏；分数必须经过 benchmark 之外的证据检验（见第 7 步）。

说明：DR 是从产品名长出来的概念，20 篇里人人都具备的特征只有"搜索"和"智能体"两个。所以 DR 的本质只能**约定**，没有现成的可以去发现。约定的理由来自第 0 步的用途。

## 2. 构念：内涵与外延分两层

### 2.1 任务层：什么算 DR 题

本质属性决定一道题有没有资格进题库。入场检查问四个问题：

- 一次检索能不能解决？
- 不联网能不能答出来？
- 专家要花多久、要看多少材料？
- 答案有没有边界，也就是能不能判断"答全了"？

外延：
- **在内**：调研型问题，答案散落在已有的公开信息里。交付形式不属于定义，本方案按场景选"带出处的报告"。
- **不在内**（负面清单）：
  - 需要做实验、产出新数据的科研；
  - 多模态材料理解；
  - 中途向用户反问；
  - 一次检索就能答的查找题。

### 2.2 能力层：什么叫做得更好

本质属性不随 Agent 变化，拉不开差距。Benchmark 测的是**各 Agent 把本质活动做到了什么程度**，维度要从本质推出来，而不是挑出来。

| 本质属性 | 质量维度 |
|---|---|
| 一次检索或单一来源解决不了 | **找全**：需要的信息覆盖了多少 |
| 得出结论 | **找对**：结论是否正确 |
| 由证据支撑 | **有据**：每条结论能否追到来源，来源是否真的这么说 |
| 整合多条信息 | **整合**：有没有得出需要多个来源合起来才成立的结论，冲突有没有处理 |
| 由用户需求驱动 | **切题**：回答的是不是用户要的 |

- 推不出来的不进排序：篇幅、文笔、格式。如有需要，另设"体验层"单列。
- 规则：每个维度都要说得清它对应哪条本质属性，说不清的不进。

## 3. 小样试跑：尽早接触真实数据

2–3 个 Prompt × 5 个 Agent，人工通读 10–15 份报告：

1. 列出真实的差异和失败类型：编造引用、事实过时、漏掉要点、答非所问……
2. 检查第 2.2 步的维度能不能覆盖这些差异。覆盖不了的，回到第 1–2 步修订。
3. 粗估成本：每份报告的评审时间、API 费用。

## 4. 关键问题与 Breakdown

按 Benchmark 的四个零件（题、标准、判卷、考场），加上计分、效度、维护来组织。

- **K1 题**：从哪来；怎么过入场检查；怎么防止被模型背下来。
- **K2 标准**：每道题的必答要点和参考结论从哪来。Breakdown 示例：
  - (a) 要点清单由谁写、谁复核？
  - (b) 报告里出现了、清单里却没有的正确内容怎么办？做法是把 5 份报告里的新结论核实后并入清单，参考 TREC 的池化和 LiveDRBench 的标准答案扩充。
  - (c) 要点过期怎么办？每条要点标注核实日期，过期就复核。
- **K3 判卷**：
  - 评委能不能上网核实（能力对等）；
  - LLM 评委的偏差（位置、篇幅、偏向自家模型）；
  - 人工复核的比例。
- **K4 考场**：实时网络还是固定语料；5 个 Agent 同一天跑；题目的截止日期。
- **K5 计分与排序**：
  - 答错和不答分开计；
  - 每道题内先排名或标准化，再跨题汇总，不直接相加原始分；
  - 多维度合并前，先看有没有谁在所有维度上都更好；剩下的在几组合理权重下各排一次，名次不变才算数；
  - 名次可信度：对题目做 bootstrap 重抽样。
- **K6 效度**：见第 7 步。
- **K7 维护**：见第 9 步。

## 6. 方案与例子

双路线排序，用同一批报告：

- **路线 A：按维度清单打分，再排名。** 能看出各 Agent 输在哪个维度；以后加入新 Agent，原有分数不变。
- **路线 B：两两比较，再排名。** 5 个 Agent 共 10 对，每对左右调换各比一次，用 Bradley–Terry 模型算出分数。相对判断比绝对打分更可靠，但分数只在这批对手之间有意义。

两条路线的排名一致才发布；不一致就排查标准或评委。

用一道题做完整示例：题目 → 入场检查 → 要点清单 → 5 份报告的维度分和比较结果 → 名次及其可信度。

## 7. 验收测试：修订循环的停止条件，不依赖你我判断

1. **扰动检验。** 只看方向，不设阈值：
   - 加 2000 字没有新信息的内容 → 分数不涨；
   - 删掉关键来源 → "找全"下降；
   - 把一个正确数字改错 → "找对"下降；
   - 换上不支持结论的引文 → "有据"下降。
2. **稳定性。** 重跑一次、换一个评委，名次的可信度不明显下降。
3. **与专家对照。** 在"一对一对报告"的层级上比较：机器判"哪份更好"与专家判断的一致率，不低于两位专家之间的一致率。
   - 每道题有 10 对，比拿 5 个 Agent 的总排名去和专家排名对照有力得多。
4. **两条路线的排名一致。**

所有阈值在看到正式结果之前写定。

注：第 3 条与心得笔记中"专家盲测 vs Agent 评测"同向。是否把它展开成一项独立研究，由你决定。

## 8. 修订循环

分析问题 → 修订第 1–6 步 → 重跑第 7 步。全部通过即停。

## 9. 维护

- 每次评测前更新题目和截止日期。
- 标准要点标注核实日期，过期就复核。
- 保留全部报告、评委输出和版本信息，以便复算。

【命名】避免用"DRBench"（据我所知已有同名 benchmark；初代 DeepResearch Bench 也常被简称为 DRB）。

## 修订记录（v1 → v2）

| 改动 | 原因 |
|---|---|
| 新增第 0 步"用途"，目标定为排序 | 用途决定定义取舍和被评对象；打分是排序的手段 |
| 定义改为"共性基线 + 明确偏离" | 23 篇里没有公认定义；DR 的本质只能约定 |
