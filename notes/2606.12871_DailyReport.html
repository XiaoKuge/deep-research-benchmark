0结论先行

  • 它是一个还拿不到手的 benchmark。仓库从 2026-06-10 建立起就只有一个 README，写着 "coming soon"，至今已经四个多月。不能拿它来跑，也无法核对论文里任何逐题层面的说法。
  • 思路和 DRB II 相反。题目从社交平台的热点需求正向写出；评分条目只写"检查什么"，不存答案；事实对不对，由评委在评测时上网去查。
  • 方法上有几处值得借鉴：
    • 按约束类型把题目拆成可以逐项检查的子任务；
    • 级联计分：没写到的内容，不给它打事实分；
    • "必须有 / 有更好"的重要性分档；
    • 逐条核验断言，算精确率；
    • 把"引用本身对不对"和"引用是否支持断言"分开统计。
  • 它的验证环节站不住：
    • 请用户打分时，看起来先给他们看了算法的子任务结果；
    • 拿来考评委的"标准答案"，是专家看过评委的判定后才定下的；
    • 事实的真值，取决于一个比部分被测系统还弱的评委能不能搜到。
    所以论文里的高一致性（κ 0.859、准确率 96.5%）不能直接当证据。
  • 适合的用法：当成一份评测设计参考来读，不要引用它的排名和一致性数字。

1它做了什么

  1. 收集热点。从微博、小红书、知乎和 Facebook、Reddit、Twitter 收集热门话题帖和用户评论。
  2. 专家写题。受雇人员根据话题和评论写出 150 道搜索任务：100 道检索型，50 道分析型。再把每道题归入 35 个细分类、10 个大领域。
  3. 拆子任务、生成条目。按 9 种约束类型把每道题拆成子任务。每个子任务配最多三条"级联"条目：指令遵循、事实性、合理性。条目由 LLM 生成，专家协助修改。
  4. 定重要性。出题人给每个子任务标出重要性档位，分 P0 / P1 / P2 / P2(a) 四档。
  5. 评测。
    • 评委是 Gemini-3-flash，配 Serper 搜索和 Jina 网页抓取。
    • 算出指令遵循、事实性、合理性三个维度的分数，再用一套规则折算成 1–4 分的"用户偏好分"。
    • 一共评了 17 个系统：5 个原生 DR 智能体、6 个"LLM + 搜索工具"、6 个"LLM + Claude Code"。
项目数字
任务150 道：100 道检索型（找齐指定实体的客观信息，只做轻量分析）、50 道分析型（话题更开放，需要自己判断该找什么）
评分条目3,546 条，平均每题 23.6 条。数的是"子任务 × 维度"的条数，不是事实的条数
子任务数论文没给。按每个子任务 1–3 条推算，在 1,182 到 3,546 之间
人工投入500 小时以上，报酬约每天 56–70 美元
评测结果
  • 用户偏好分最高的是 GPT-5.4 + 搜索工具，2.89；原生 DR 智能体在 2.17–2.48 之间；17 个系统都没到 3 分"可接受"。
  • 指令遵循 0.92–0.99，事实性 0.61–0.84，合理性 0.66–0.93。
  • 子任务全部条目都通过的比例只有 0.12–0.48。

3底层逻辑：真值从"答案"换成"现场核验"

论文第 1 节批评了两类已有做法：

  • 题目：由领域专家出的专业题，"不太会出现在真实场景里"；而且是静态的，有污染风险。
  • 评分：按粗粒度维度打分、再线性相加，可解释性差，也量化不了用户的感受。

它的应对可以归纳成四步：

  1. 题目真实：从热点和评论里提炼需求，由人写题。
  2. 要求可查：把题目拆成子任务，每个子任务先问"做到了没有"。这一步只看报告本身，不需要知道答案。
  3. 事实现场查：从报告里抽出断言，评委上网核验，算出"说对的比例"。
  4. 贴近用户：按子任务对用户的重要程度做非线性汇总，得出 1–4 分。

整套方法里没有一份"标准答案"。和 DRB II 对照：

  • DRB II：信任来自一篇已发表的文章，所以它的问题是"文章对不对、全不全"。
  • DailyReport：信任来自评委在评测那一刻的搜索结果，所以它的问题变成"评委搜得到吗、搜到的对吗、换个时间还一样吗"。

43,546 条评分条目怎么来

写题的要求（§3.2、附录 A.1）

  • 三条原则：真实（反映特定人群的真实需求）、清晰（避免含糊表述）、安全（不触发安全拒答）。
  • 附录还列了几条：依赖工具（必须搜索才能答）、只用文本、各维度互不重叠。
  • 流程：标注员先读热帖和评论，找出常见需求，过滤掉不安全、太窄、含糊或不适合写成日报的话题。写题人把选中的话题写成任务。另有审核人检查是否清晰、真实、安全、依赖搜索、分类一致。

拆子任务（§3.3、附录 A.2）

9 种约束类型：

  • 内容：必须输出哪些核心信息；
  • 范围：时间、地域、领域、来源等边界；
  • 完整性：数量和覆盖的标准；
  • 数量：字数、条目数；
  • 格式：结构和排版；
  • 设定：给定的背景、角色、前提或数据；
  • 属性：风格和视角；
  • 行为规则：必须遵循的方法和步骤；
  • 功能：输出要达到的实际用途。

拆分有三条原则：

  • 原子性：一个子任务通常只对应一种约束。范围和完整性约束例外，它们不能单独成为子任务。
  • 覆盖：所有子任务合起来要覆盖原题的全部要求。
  • 可追溯：子任务必须出自原题，不能凭空添加。

三个维度

维度条目的样子（图 1）判法是否需要答案
指令遵循"是否分析了 n？"0 / 0.5 / 1不需要。只看报告有没有做到
事实性"所给事实是否准确？"抽出的断言中核验为真的比例不预存。评委用 Serper 和 Jina 现场核验
合理性"推理是否合理？"0 / 0.5 / 1不需要。只根据上下文判断推理是否成立

并不是每个子任务都有事实性和合理性条目，所以平均每题只有 23.6 条。真正被核验的断言要到评测时才从报告里抽出来，每份报告可能有几十到上百条。

5分数怎么算

指令遵循  Ins = 各子任务 ins 的平均
事实性    Fac = Σ ins·fac ÷ Σ ins     （只统计带事实性条目的子任务）
合理性    Rat = Σ ins·rat ÷ Σ ins     （只统计带合理性条目的子任务）
子任务综合 o = ins × (fac + rat) ÷ 2

级联的含义：指令没做到（ins = 0），事实和推理都不计分。所以事实性分数衡量的是"写出来的那部分有多对"。

重要性分档：由出题人做一个思想实验："只有这一项没做到时，用户会给几分？"

  • P0：缺了就完全没用（1 分）；
  • P1：缺了就有明显缺陷（2 分）；
  • P2：单独缺一项还能接受（3 分）；
  • P2(a)：单独缺一项能接受，缺几项就降到 2 分。

用户偏好分（算法 1）：按档位的完成情况查规则给分。

  • 全部做到：4 分；
  • P0 全挂，或 P1 均值低于 0.3，或 P0 和 P1 均值都低于 0.5：1 分；
  • P0 均值 ≥ 0.5、P1 全部大于 0、P2(a) 至少有一项大于 0、P1 均值 ≥ 0.7：3 分；
  • 其余情况：2 分。

这里的"P1 均值"是把 P1 各项和 P2(a) 组的均值放在一起算的。

两点值得注意：

  • 阈值 0.3 / 0.5 / 0.7 是手定的，论文没说依据。
  • 普通 P2 子任务只在"全部做到才给 4 分"那一条里出现。它们做得好不好，对 1–3 分没有任何影响。

6弱在哪：拆开论证链

环节要成立的命题表现依据
① 打分评委在每个子任务上判得准中

6.1 没有数据，也没有代码

  • 论文摘要写着数据和代码"已公开"，但仓库里只有一个 README："The benchmark and evaluation scripts are coming soon..."。三次提交都在 2026-06-10。
  • HuggingFace 上，AGI-Eval 组织下有 5 个数据集，没有 DailyReport。
  • 后果一：算法 1 的阈值、条目的写法、断言抽取和核验的提示词，全都无法复现。
  • 后果二："支持持续更新"无法验证。论文没写更新机制和版本管理，而题目基于 2026 年上半年的热点，到现在已经不"新"了。

6.2 事实的真值取决于评委能不能搜到

  • 核验断言的是 Gemini-3-flash 加 Serper 和 Jina。被测系统里有 GPT-5.4、Claude Opus 4.6、Gemini 3.1 Pro，评委的搜索和判断能力不一定比它们强。
  • 评委搜不到，正确的断言就会被判错；评委搜到了错误来源，错误的断言就会被判对。
  • 热点信息变化快，网页会被修改或删除，隔一段时间重评，事实性分数就可能变了。论文没有存档被引网页，也没有规定以哪个时间点为准。

6.3 选评委、验证评委，用的是同一批数据，而且"标准答案"不独立

  • 两个实验数字相同。表 5"评委选择"里 Gemini-3-flash 的准确率（96.5 / 94.2 / 95.3）和 §5.5"指标验证"报告的数字完全相同。看起来是同一个实验报告了两次：在哪批数据上选出了评委，就在哪批数据上验证它。
  • 标准答案看过评委的判定。指令遵循的标准答案是这样定的：人工标注员和评委各判一遍，再由专家"看过两边的结果"后裁决。评委 96.5% 高于人工标注员的 88.4%，有一部分是因为裁决本身参考了评委的判定。
  • 落选的评委不一定更差。Claude-4.5-Sonnet 在事实性（94.5）和合理性（95.7）上都高于 Gemini-3-flash，最终选后者主要是因为便宜（平均成本 0.45 美元对 2.53 美元，论文没写计价单位）。

6.4 用户偏好的验证不独立

users are given the generated reports and subtask results, and assign an overall score from 1 to 4§5.5
  • 评分人拿到的除了报告，还有"子任务结果"（subtask results）。最自然的理解是算法给出的子任务判定。如果是这样，算法分和人的评分一致，有一部分是因为人看了算法分。论文没说清楚这一点，本身也是个问题。
  • 正文说"加权 Cohen's kappa 0.859"。用图 6 的混淆矩阵重算：0.859 其实是不加权的 kappa，线性加权是 0.876，二次加权是 0.901（图上标的就是 0.901）。一致性本身确实高，只是标注有误。
  • 300 个样本里，用户评 3 分的有 179 个（60%），评 4 分的只有 6 个，分布很集中。
  • 抽样单位有歧义：正文说"随机抽 300 个子任务"，但用户打的是"整份任务"的分，两者不是同一个层级。

6.5 "用户视角"其实是出题人视角

  • 重要性档位是出题人想象"缺了这一项用户会给几分"得出的，没有让真实用户来定。
  • 阈值是手写的。所以"最高 2.89 分、达不到 3 分可接受"，部分是这套规则的定义带来的结果。

6.6 事实性只算精确率

  • 事实性 = 核验为真的断言 ÷ 抽出的断言。少写、只写有把握的内容，这一项反而分高。
  • "列全了没有"归在指令遵循的完整性约束里。但条目里不存答案，评委怎么知道 QS 前 100 里漏了两所大学？只能评测时现查。论文没说清楚，数据不公开也无从核对。

6.7 组间比较可能有混杂因素

  • "LLM + 搜索工具"和"LLM + Claude Code"两组用了统一的系统提示词（附录 C）：不许用自身知识、至少 2000 字、统一的 [n] 引用格式和参考文献列表。这正好是后面核验流程需要的格式。
  • 原生 DR 智能体的配置（附录 B.4.1）只写了把超时放宽到 1,800 秒，没说有没有做引用格式统一。
  • 所以"原生 DR 智能体更差"的结论，有一部分可能来自输出格式和核验流程的匹配程度。

6.8 稳定性检验说得不清楚

  • 表 4 只挑了 3 个模型，各重复 3 次，标准差很小。但论文没说重复的是"重新生成报告"还是"同一份报告重新评分"。如果是后者，就只反映了评委的稳定性，没有反映 Agent 自身的波动。
  • 重复运行的均值和主表对不上。比如 Gemini 3.1 Pro + 搜索的事实性，表 3 是 0.730，表 4 是 69.9 ± 2.7，主表数字落在一个标准差之外。

7它做对了什么

  • 题目从真实需求正向写出。不从现成答案倒推，题目自然、简短，问的是现状，避开了 DRB II"题目就是提纲"的问题。
  • 按约束类型拆子任务。把一个笼统的 Prompt 变成可以逐项检查的清单。9 种约束类型本身就是一份好用的检查表。
  • 级联计分。先看做没做到，再看对不对、推理好不好，避免给没写出来的内容打事实分。
  • 显式的重要性分档。把"必须有"和"有更好"区分开来并写进计分规则，比各项一律平均更接近人的判断。
  • 逐条核验断言、算精确率。补上了 DRB II 只算召回的盲区。
  • 把引用的两个问题分开统计（附录表 6）。"引用本身对不对"是 0.55–0.77，"断言是否忠于引用"是 0.74–0.86，两者分开看更清楚。
  • 给出了重复评测的标准差。虽然只做了 3 个模型，但大多数开放式 benchmark 连这一步都没做。

9对"同一 Prompt、5 个 Agent"的启示

  1. 按 9 种约束类型拆出要求清单，并给每一项标 P0 / P1 / P2。这一步在运行之前做，写进预登记。
  2. 级联计分：先判每个子任务做没做到，再对做到的部分评事实和推理。
  3. 逐条核验断言，但对照运行时存档的网页，不要现搜。这样避开网页漂移和评委搜索能力的问题。5 份报告的断言可以全部核验，矛盾的交专家裁决。
  4. 召回不能少：专家必答清单，加上 5 个 Agent 各跑 3 次的汇总池。这是 DailyReport 缺的那一半。
  5. 验证必须独立：
    • 请专家或用户打分时，不给他们看算法的结果；
    • 用来考评委的标准答案，在评委判定之前就定好；
    • 选评委和验证评委用两批不同的样本。
    这是这篇论文最值得吸取的教训。
  6. 统一输出格式要对所有 Agent 一视同仁，或者在核验之前统一做格式归一。不然比的是谁的格式更合核验流程，而不是谁研究得好。
